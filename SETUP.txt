RAFT5FS: SETTING UP THE KV STORE, FILESYSTEM SERVERS AND MOUNTS
===============================================================

raft5fs has three tiers:

  raft5 cluster      the key-value store everything lives in. Only the
  (raft5-server)     filesystem servers may talk to it.

  filesystem         stateless; hold the store credentials, check logins
  servers            and grants. Run as many as you like against one
  (raft5fs-server)   store.

  mounts             one per user per machine. Log in as a user, encrypt
  (raft5fs-fuse)     and decrypt, buffer and cache, and use whichever
                     server answers.

    user's mount --(TLS, user login)--> fs server --(mTLS, service login)--> raft5

Everything is encrypted on the users' machines: file contents and names
are sealed by the mount before they leave it, and users' passwords never
reach a server. Neither the store nor the filesystem servers -- nor
whoever runs them -- can read what is in the filesystem (section 8 says
exactly what they can see). Access is by grants of directories to users
(section 7).

The steps below set up one store node, one filesystem server and one
mount on a single machine, with TLS everywhere. Section 9 covers adding
more of each.

Commands are run from a scratch directory, here called $WORK. Ports used:

  27051  raft5 client API      27052  raft5 peer API
  27060  filesystem server


-------------------------------------------------------------------------
1. BUILD
-------------------------------------------------------------------------

The store (from the jmeisel_raft5 repository):

  cd jmeisel_raft5
  cargo build --release -p raft5-server -p raft5-client
  # -> target/release/raft5-server  (a store node)
  # -> target/release/raft          (the store's admin shell)

The filesystem (from this repository):

  cd jmeisel_raft5_fuse
  cargo build --release
  # -> target/release/raft5fs-server
  # -> target/release/raft5fs-fuse
  # -> target/release/raft5fs-share  (accounts and sharing)

Mounting needs FUSE 3 (`fusermount3`), e.g. the `fuse3` package.

The examples below assume these binaries are on your PATH.


-------------------------------------------------------------------------
2. CERTIFICATES AND SECRETS
-------------------------------------------------------------------------

One self-signed certificate, used by every tier: the store serves with it
and requires it of clients (mTLS), the filesystem servers present it to
the store and serve their own clients with it, and every client trusts
it. (For separate certificates per tier, or your own CA, see TLS.txt in
the jmeisel_raft5 repository; the requirements there apply here too.)

  cd $WORK
  openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:prime256v1 \
    -nodes -days 365 -subj "/CN=raft5fs" \
    -addext "subjectAltName=DNS:localhost,IP:127.0.0.1" \
    -addext "basicConstraints=critical,CA:FALSE" \
    -addext "extendedKeyUsage=serverAuth,clientAuth" \
    -keyout key.pem -out cert.pem

List every host name or IP that clients will dial in subjectAltName.

Then two secrets and a password:

  # The store's token-signing secret.
  head -c 48 /dev/urandom | base64 > jwt.secret

  # What the filesystem servers sign sessions with. Every filesystem
  # server needs the same file. Anyone holding it can act as any user --
  # though, everything being encrypted, still not read anything they
  # couldn't before -- so keep it secret.
  head -c 48 /dev/urandom > token.key

  # The store's first administrator's password.
  echo 'choose-an-admin-password' > admin.pw

  chmod 600 key.pem jwt.secret token.key admin.pw

Only the users' machines need cert.pem; key.pem, jwt.secret and token.key
stay on the servers.


-------------------------------------------------------------------------
3. START AND BOOTSTRAP THE STORE
-------------------------------------------------------------------------

Start a node:

  raft5-server --id n1 --db $WORK/db \
    --client-addr 127.0.0.1:27051 --peer-addr 127.0.0.1:27052 \
    --jwt-secret-file jwt.secret \
    --initial-admin-user admin --initial-admin-password-file admin.pw \
    --client-tls-cert cert.pem --client-tls-key key.pem \
    --client-tls-ca cert.pem

--client-tls-ca is what makes the store require a client certificate.
Users never get key.pem, so they can't even connect to the store.

Open the admin shell in another terminal. It asks for admin's password:

  raft --nodes https://127.0.0.1:27051 \
    --ca-cert cert.pem --cert cert.pem --key key.pem --user admin

In the shell, bootstrap the cluster, create the filesystem servers'
account and lock the store down. create_user asks for its password.

  raft> bootstrap n1
  raft> create_user raft5fs
  raft> acl_set "" user:raft5fs=write
  raft> quit

  - raft5fs  is the service account the filesystem servers work as.
             Filesystem users don't get store accounts: they log in to
             the filesystem servers, with keys of their own (section 5).
  - acl_set ""  puts an ACL on the empty prefix, which governs every
             key: only raft5fs may read or write anything. Without it,
             every key is open to any logged-in account.

The --initial-admin-* flags only matter until the bootstrap. After that
the stored admin account takes over, and they can be left off.


-------------------------------------------------------------------------
4. START THE FILESYSTEM SERVER
-------------------------------------------------------------------------

The filesystem servers' store options, used here and in section 5:

  export RAFT5FS_STORE_PASSWORD='<the raft5fs password>'
  STORE="--store-user raft5fs --store-ca cert.pem \
         --store-cert cert.pem --store-key key.pem"

  raft5fs-server --listen 127.0.0.1:27060 \
    --token-key-file token.key \
    --tls-cert cert.pem --tls-key key.pem \
    $STORE https://127.0.0.1:27051

The first server to start on an empty store creates the filesystem.

  --chunk-size  how files are split into store keys (default 1M). Fixed
                when the filesystem is created.
  --session-ttl  how long a login lasts, in seconds (default 86400),
                before the mount logs in again on its own.
  --identity-ttl  how long, in seconds, a server trusts an account to
                still exist before looking again (default 5): how long
                removing a user takes to reach one who is mounted.

A store made by an older raft5fs, which could make unencrypted
filesystems, is refused: there is no migrating one.

Leaving off --tls-cert/--tls-key serves in plaintext, and the server
warns you: what is stored stays encrypted, but sessions cross the
network in the clear, for anyone watching to reuse.


-------------------------------------------------------------------------
5. ADD USERS
-------------------------------------------------------------------------

Adding a user issues a one-time code (with the store options from
section 4):

  raft5fs-server user add alice $STORE https://127.0.0.1:27051

Hand the code to alice, who runs, on her own machine:

  raft5fs-share --user alice --ca cert.pem enrol <CODE> https://127.0.0.1:27060

She chooses her password there. Her machine makes her key pair, stores
the private key on the server sealed under a key only her password
yields, and prints the key's fingerprint. She should note it: it is how
others can check, when sharing with her, that the server handed them her
real key (7.3).

Her password is stretched on her machine into a login secret, which is
all a server ever gets. To change it -- everything shared with her stays
readable:

  raft5fs-share --user alice --ca cert.pem passwd https://127.0.0.1:27060

A forgotten password can't be recovered: nothing on the servers opens
her private key without it. `user add alice` again issues a new code; she
enrols again with a new key pair, and whatever was shared with her has
to be shared again. Others will be told her key changed (7.3).

  raft5fs-server user list $STORE https://127.0.0.1:27051
  raft5fs-server user del alice $STORE https://127.0.0.1:27051

`user del` removes the account and every grant made to it. A mounted user
who is removed is refused within --identity-ttl.


-------------------------------------------------------------------------
6. MOUNT
-------------------------------------------------------------------------

As the local user who will use the mount (not root):

  mkdir -p ~/raft5fs
  raft5fs-fuse --user alice --ca cert.pem ~/raft5fs https://127.0.0.1:27060

It asks for alice's password on the terminal, or reads it from the
RAFT5FS_PASSWORD environment variable. It runs in the foreground; leave
it running, and use ~/raft5fs from another shell.

The root of the mount isn't the filesystem's real root. It lists only
what has been shared with alice, each under the name it was shared as,
and nothing above those directories is reachable at all. A new user's
root is empty. `mkdir` there makes a volume: a new top-level directory,
shared with its maker alone. `rmdir` there removes an empty volume (and
every grant of it). Nothing else can be made, moved or removed in the
root.

  mkdir ~/raft5fs/photos
  cp -r ~/Pictures/2024 ~/raft5fs/photos/
  ls -l ~/raft5fs/photos

There are no owners in the filesystem: everything shows the local user
who mounted it as its owner, and chown to anyone else is refused.
Permission bits are kept and shown (so `chmod +x` works), but grants
decide who may read and write (section 7).

Everything done through the mount is done as alice, whichever local user
does it. That is why the mount is only usable by the local user who
mounted it. Each person mounts with their own login.

  --cache-size <SIZE>  memory for caching file data, decrypted (default
                     64M, 0 disables). A cached chunk is checked with a
                     server on every read -- a few bytes, not the chunk --
                     so it is never stale.
  --tls-server-name <NAME>  check the server certificate against NAME
                     instead of the host in the address.
  --no-write-buffer  store every write at once instead of buffering
                     small writes (slower; mostly for debugging).

Give several server addresses to fail over between them:

  raft5fs-fuse --user alice --ca cert.pem ~/raft5fs \
    https://fs1:27060 https://fs2:27060

To unmount:

  fusermount3 -u ~/raft5fs

Buffered writes are stored before the unmount completes. A program
that needs to know its data is stored should call fsync, or check the
result of close.

Not supported: hard links, symlinks, device files, and atomically
swapping two names (renameat2 RENAME_EXCHANGE).


-------------------------------------------------------------------------
7. SHARING
-------------------------------------------------------------------------

7.1 Grants

Grants are of directories, and cover everything under them. With
raft5fs-share, a path starts at an entry of the root, as the mount shows
it:

  raft5fs-share --user alice --ca cert.pem \
    grant photos/2024 bob --ro --name from-alice https://127.0.0.1:27060

bob's root now shows from-alice. --ro makes the grant read-only, and
writes under it then fail with "Read-only file system"; without it bob
may change anything under it, and share it on. To share, alice needs a
read-write grant of the directory -- which she has of every volume she
made.

  raft5fs-share ... grants photos/2024 <server>     who holds it, and how

Grants alone decide access, and are checked on every request, so a grant
taken back stops even files bob has open, at once.

7.2 Revoking

  raft5fs-share ... revoke photos/2024 bob <server>

A revocation gives the directory a new key, and new keys for everything
under it before anything new is written there: what is written after it
is sealed under keys bob never had. What bob could read before, he may
have kept a copy of; revoking can't take that back. Revoking a grant of
a directory needs a grant of the directory above it (its new key is
sealed under that one's), except for a volume.

7.3 Whose key?

Sharing with bob seals the directory's key to bob's public key, and only
the server can say what that is. raft5fs-share pins each user's key the
first time it seals to them, in ~/.config/raft5fs/known_keys (or
--known-keys), and refuses a different one after that. Check the
fingerprint `grant` prints against the one bob saw when he enrolled. If
he really did enrol again, check his new fingerprint with him, then:

  raft5fs-share --user alice forget-key bob

Pins are kept per user name, so keep a known-keys file per filesystem.


-------------------------------------------------------------------------
8. WHAT THE SERVERS CAN AND CAN'T DO
-------------------------------------------------------------------------

They can't read file contents, names (of files, directories, or what a
grant is called), or passwords; nor forge or alter data without the
change being detected when it is read.

They can see:

  - the shape of the tree, inode numbers, sizes, permission bits and
    times;
  - who is granted what, read-only or not, and who reads and writes
    which inodes, and when;
  - the tag each name is filed under. The tag of a name doesn't change
    when the directory's key does, so someone revoked who also got hold
    of the raw store could test guesses at the names of new files in a
    directory they used to have.

And as the ones holding the data, they can always lose it, withhold
it, change what isn't sealed (sizes, times, permission bits, the tree's
shape), or hand back an older version of a chunk that was really written
once (sealing proves where data came from, not that it is the latest).
A malicious server could also show a user a directory it made up
itself, or answer a lookup with the wrong inode (listings are checked;
single lookups aren't). The fingerprints in 7.3 are what stop it reading
what users share with each other.

What it costs:

  - The server can't patch an encrypted chunk, so a write smaller than
    a chunk changes the whole chunk: from the mount's cache if it has
    it, or else read, changed and re-sealed. Small, scattered writes to
    files the mount hasn't touched cost more; a smaller --chunk-size,
    chosen when the filesystem is created, helps.
  - Each chunk is stored 44 bytes larger.
  - A revocation scans every grant in the filesystem. Fine for
    hundreds; slow for very many.

local-fs (in utils) runs a whole installation on one machine, for
trying all this out.


-------------------------------------------------------------------------
9. MORE THAN ONE OF EACH
-------------------------------------------------------------------------

More filesystem servers: start another raft5fs-server, the same way as
in section 4, on any machine that can reach the store, with the same
token.key. Servers keep no state of their own, so a mount can use any of
them, and an open file survives its server restarting.

Changing token.key logs every mount out. Mounts log back in on their
own, from the login secret they kept.

More store nodes: start each node with its own --id and --db, plus the
peer TLS flags (--peer-tls-cert, --peer-tls-key, --peer-tls-ca; every
node must agree), and use --advertise / --advertise-client when nodes
dial each other by addresses other than the ones they bind. Then add it
from the admin shell, connected to the existing cluster:

  raft> add_server https://<new-node>:<peer-port>

See TLS.txt in the jmeisel_raft5 repository for the peer certificate
requirements. Give filesystem servers every store node's client address
as seeds.


-------------------------------------------------------------------------
10. TROUBLESHOOTING
-------------------------------------------------------------------------

  "login refused: the username or password was wrong"
      Also what a user who hasn't enrolled yet gets (section 5).

  "no such enrolment code"
      The code is wrong, was issued to someone else, or was used: codes
      work once. `user add` issues another.

  "Operation not permitted" making a file at the top of a mount
      Only volumes go there: `mkdir` one, and put files in it.

  "the server gave a different key for <user> than before"
      Either they enrolled again or the server is lying. Check their
      fingerprint with them before `raft5fs-share forget-key <user>`.

  "... can't reach" (revoke)
      Revoking a grant of a directory takes a grant of the one above it;
      ask someone who has one, or revoke at the volume.

  "this store holds a filesystem made by an older, unencrypted raft5fs"
      There is no migrating it; start from an empty store.

  "cannot log in to the store as raft5fs" (filesystem server)
      RAFT5FS_STORE_PASSWORD is wrong, or the store certificate options
      don't match the store's (--store-ca, and --store-cert/--store-key
      if the store requires client certificates).

  A server that "did not answer"
      Over TLS this is often a refused handshake, not a dead server: a
      missing client certificate, or a certificate whose
      subjectAltName doesn't cover the address dialed.
