RAFT5FS: SETTING UP THE KV STORE, FILESYSTEM SERVERS AND MOUNTS
===============================================================

raft5fs has three tiers:

  raft5 cluster      the key-value store everything lives in. Only the
  (raft5-server)     filesystem servers may talk to it.

  filesystem         stateless; hold the store credentials, check logins
  servers            and grants. Run as many as you like against one
  (raft5fs-server)   store.

  mounts             one per user per machine. Log in as a user, encrypt
  (raft5fs mount)    and decrypt, buffer and cache, and use whichever
                     server answers.

    user's mount --(TLS, user login)--> fs server --(mTLS, service login)--> raft5

Everything is encrypted on the users' machines: file contents and names
are sealed by the mount before they leave it, and users' passwords never
reach a server. Neither the store nor the filesystem servers -- nor
whoever runs them -- can read what is in the filesystem (section 9 says
exactly what they can see). Access is by grants of directories to users
(section 7).

The steps below set up one store node, one filesystem server and one
mount on a single machine, with TLS everywhere. Section 10 covers adding
more of each.

Commands are run from a scratch directory, here called $WORK. Ports used:

  27051  raft5 client API      27052  raft5 peer API
  27060  filesystem server


-------------------------------------------------------------------------
1. BUILD
-------------------------------------------------------------------------

The store (from the jmeisel_raft5 repository):

  cd jmeisel_raft5
  cargo build --release -p raft5-server -p raft5-client
  # -> target/release/raft5-server  (a store node)
  # -> target/release/raft          (the store's admin shell)

The filesystem (from this repository):

  cd jmeisel_raft5_fuse
  cargo build --release
  # -> target/release/raft5fs-server  (a filesystem server, and its admin)
  # -> target/release/raft5fs         (everything a user does: mount or
  #                                    serve over WebDAV, enrol, share,
  #                                    prune; `raft5fs help`)

Mounting needs FUSE 3 (`fusermount3`), e.g. the `fuse3` package. Where
there is no FUSE (a Mac without macFUSE, a container without /dev/fuse),
build the client without it and use WebDAV instead (section 6.1):

  cargo build --release -p raft5fs --no-default-features --features webdav

Or download the client, `raft5fs`, already built. Each release on
GitHub has one file per platform, plus SHA256SUMS to check them:

  raft5fs-linux-x86_64      mount (FUSE 3) and WebDAV
  raft5fs-macos-aarch64     WebDAV only (Apple Silicon)
  raft5fs-android-aarch64   WebDAV only, for Termux (section 14)

  url=https://github.com/jonathanmeisel/jmeisel_raft5_fuse/releases/latest/download
  curl -LO $url/raft5fs-linux-x86_64 -LO $url/SHA256SUMS
  sha256sum -c SHA256SUMS --ignore-missing    # macOS: shasum -a 256 -c ...
  install -m 755 raft5fs-linux-x86_64 ~/.local/bin/raft5fs

Or let deploy/get-raft5fs.sh do all of that: it picks this machine's
binary, checks it, and installs it as ~/bin/raft5fs (--dest DIR for
elsewhere; a version such as v0.2.0 for a given release):

  curl -fsSLO https://raw.githubusercontent.com/jonathanmeisel/jmeisel_raft5_fuse/master/deploy/get-raft5fs.sh
  sh get-raft5fs.sh

`latest` is the newest release; put e.g. download/v0.2.0 in its place
for a given one. A binary downloaded with curl runs as is; one
downloaded with a browser on macOS is blocked until
`xattr -d com.apple.quarantine raft5fs`, because it isn't signed. The
servers aren't released this way: build them as above.

The examples below assume these binaries are on your PATH.


-------------------------------------------------------------------------
2. CERTIFICATES AND SECRETS
-------------------------------------------------------------------------

One self-signed certificate, used by every tier: the store serves with it
and requires it of clients (mTLS), the filesystem servers present it to
the store and serve their own clients with it, and every client trusts
it. (For separate certificates per tier, or your own CA, see TLS.txt in
the jmeisel_raft5 repository; the requirements there apply here too.)

  cd $WORK
  openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:prime256v1 \
    -nodes -days 365 -subj "/CN=raft5fs" \
    -addext "subjectAltName=DNS:localhost,IP:127.0.0.1" \
    -addext "basicConstraints=critical,CA:FALSE" \
    -addext "extendedKeyUsage=serverAuth,clientAuth" \
    -keyout key.pem -out cert.pem

List every host name or IP that clients will dial in subjectAltName.

Then two secrets and a password:

  # The store's token-signing secret.
  head -c 48 /dev/urandom | base64 > jwt.secret

  # What the filesystem servers sign sessions with. Every filesystem
  # server needs the same file. Anyone holding it can act as any user --
  # though, everything being encrypted, still not read anything they
  # couldn't before -- so keep it secret.
  head -c 48 /dev/urandom > token.key

  # The store's first administrator's password.
  echo 'choose-an-admin-password' > admin.pw

  chmod 600 key.pem jwt.secret token.key admin.pw

Only the users' machines need cert.pem; key.pem, jwt.secret and token.key
stay on the servers.


-------------------------------------------------------------------------
3. START AND BOOTSTRAP THE STORE
-------------------------------------------------------------------------

Start a node:

  raft5-server --id n1 --db $WORK/db \
    --client-addr 127.0.0.1:27051 --peer-addr 127.0.0.1:27052 \
    --jwt-secret-file jwt.secret \
    --initial-admin-user admin --initial-admin-password-file admin.pw \
    --client-tls-cert cert.pem --client-tls-key key.pem \
    --client-tls-ca cert.pem

--client-tls-ca is what makes the store require a client certificate.
Users never get key.pem, so they can't even connect to the store.

Open the admin shell in another terminal. It asks for admin's password:

  raft --nodes https://127.0.0.1:27051 \
    --ca-cert cert.pem --cert cert.pem --key key.pem --user admin

In the shell, bootstrap the cluster, create the filesystem servers'
account and lock the store down. create_user asks for its password.

  raft> bootstrap n1
  raft> create_user raft5fs
  raft> acl_set "" user:raft5fs=write
  raft> group_add backup-operators user:raft5fs
  raft> quit

  - raft5fs  is the service account the filesystem servers work as.
             Filesystem users don't get store accounts: they log in to
             the filesystem servers, with keys of their own (section 5).
  - acl_set ""  puts an ACL on the empty prefix, which governs every
             key: only raft5fs may read or write anything. Without it,
             every key is open to any logged-in account.
  - group_add backup-operators  lets raft5fs take and remove snapshots
             (section 8) and backups (section 13). It can already read
             every key, so this gives it nothing new to read.

The --initial-admin-* flags only matter until the bootstrap. After that
the stored admin account takes over, and they can be left off.


-------------------------------------------------------------------------
4. START THE FILESYSTEM SERVER
-------------------------------------------------------------------------

The filesystem servers' store options, used here and in section 5:

  export RAFT5FS_STORE_PASSWORD='<the raft5fs password>'
  STORE="--store-user raft5fs --store-ca cert.pem \
         --store-cert cert.pem --store-key key.pem"

  raft5fs-server --listen 127.0.0.1:27060 \
    --token-key-file token.key \
    --tls-cert cert.pem --tls-key key.pem \
    $STORE https://127.0.0.1:27051

The first server to start on an empty store creates the filesystem.

  --chunk-size  how files are split into store keys (default 1M). Fixed
                when the filesystem is created.
  --session-ttl  how long a login lasts, in seconds (default 86400),
                before the mount logs in again on its own.
  --identity-ttl  how long, in seconds, a server trusts an account to
                still exist before looking again (default 5): how long
                removing a user takes to reach one who is mounted.

To keep large files' data in an S3-compatible bucket rather than in the
store, see section 12.

A store made by an older raft5fs -- one that could make unencrypted
filesystems, or one whose grants and names were sealed differently -- is
refused: there is no migrating one.

Leaving off --tls-cert/--tls-key serves in plaintext, and the server
warns you: what is stored stays encrypted, but logins and sessions would
cross the network in the clear, for anyone watching to reuse -- and a
login is enough to test password guesses against. The clients refuse to
talk to such a server unless given --insecure-plaintext (and http://
addresses): for throwaway setups only.


-------------------------------------------------------------------------
5. ADD USERS
-------------------------------------------------------------------------

Adding a user issues an invitation (with the store options from section
4, and how users reach the filesystem servers):

  raft5fs-server user add alice --invite-server https://127.0.0.1:27060 \
    --invite-ca cert.pem $STORE https://127.0.0.1:27051

The invitation is one line: alice's one-time enrolment code, the servers'
addresses and the CA certificate to trust for them. It is as secret as
the code -- whoever has it can enrol as alice -- so hand it to her alone.
She runs, on her own machine:

  raft5fs enrol 'raft5fs-invite:1:...'

She chooses her password there: at least 12 characters, and it is worth
more. Her machine makes her key pair, stores the private key on the
server sealed under a key only her password yields, and saves a profile
-- ~/.config/raft5fs/profiles/alice.toml, with the CA beside it -- so
that no other command needs to be told the servers, the CA or her name.
It prints her key's fingerprint, as twelve words (and in hex). She gives
it to the people she shares with: it is how they check that the server
handed them her real key (7.3). `raft5fs whoami` shows it again, worked
out on her machine from her own key pair.

(Without --invite-server and --invite-ca, `user add` prints only the
code, and alice enrols with `raft5fs enrol <CODE> --user alice --ca
cert.pem --server https://127.0.0.1:27060`, which saves the same
profile.)

Her password is stretched on her machine (Argon2id, 64 MiB, three
passes) into a login secret, which is all a server ever gets. But a
server that wanted to could test guesses at her password against that
secret, as fast as it can stretch them -- and everything shared with her
comes down to her password -- so it should be one no one would guess.
To change it -- everything shared with her stays readable:

  raft5fs passwd

Every command uses her profile when it is the only one. With several,
pick one with --profile; any option given (--user, --server, --ca,
--known-keys...) wins over the profile's. `raft5fs profile list` and
`raft5fs profile show` show them.

A forgotten password can't be recovered: nothing on the servers opens
her private key without it. `user add alice` again issues a new code; she
enrols again with a new key pair, and whatever was shared with her has
to be shared again. Others will be told her key changed (7.3). Nor can
she open what was shared with her in snapshots taken before (section 8):
those were sealed to her old key.

  raft5fs-server user list $STORE https://127.0.0.1:27051
  raft5fs-server user del alice $STORE https://127.0.0.1:27051

`user del` removes the account and every grant made to it. A mounted user
who is removed is refused within --identity-ttl. It doesn't give anything
new keys, as a revocation does (7.2): to shut someone out of what is
written from then on, even should they get hold of the raw store,
revoke their grants first.

Capabilities decide what a user may start, beyond what is shared with
them: `volumes` (make top-level folders), `invite` (invite new users)
and `links` (make public links). `user add` gives `volumes` alone unless
told otherwise (--no-volumes, --invite, --links); users added before
capabilities existed have `volumes`. `user set` changes them:

  raft5fs-server user add carol --no-volumes ... $STORE https://127.0.0.1:27051
  raft5fs-server user set alice --invite on $STORE https://127.0.0.1:27051

With `invite`, alice invites others herself, giving them at most what
she may do, only under names nobody has, and at most 10 at a time:

  raft5fs invite dave [--volumes] [--invite] [--links]
  raft5fs invites                    # hers that nobody has used yet
  raft5fs invites --cancel dave

For her invitations to hold the servers' addresses and CA, as `user
add`'s do, serve with the same --invite-server and --invite-ca options.
Without them she gets only a code. `raft5fs whoami` shows what she may
do.

With `links`, she can make public links: read-only access to one
directory for anyone with the URL, through the web app, without an
account:

  raft5fs link create photos/2024 --expires 7d --app https://files.example.com
  raft5fs link list
  raft5fs revoke photos/2024 link-abcdefghijkl

A link is an account whose password is a random secret in the URL's
fragment (never sent to a server). It can only read the directory it was
made for. Anyone who can write the directory can revoke it, as for a
person, and that deletes the link's account. They can also see the link
again (`raft5fs grants` and `link list` show it): its secret is kept in
the directory's sealed list of who it is shared with. An expired link can't log in, but keeps its share until it is
revoked, so revoke it to re-encrypt the directory.


-------------------------------------------------------------------------
6. MOUNT
-------------------------------------------------------------------------

As the local user who will use the mount (not root):

  mkdir -p ~/raft5fs
  raft5fs mount ~/raft5fs

It asks for alice's password on the terminal, or reads it from the
RAFT5FS_PASSWORD environment variable. It runs in the foreground; leave
it running, and use ~/raft5fs from another shell. (Without a profile:
`raft5fs --user alice --ca cert.pem --server https://127.0.0.1:27060
mount ~/raft5fs` -- --ca is required, see section 4.)

The root of the mount isn't the filesystem's real root. It lists only
what has been shared with alice, each under the name it was shared as,
and nothing above those directories is reachable at all. A new user's
root is empty. `mkdir` there makes a volume: a new top-level directory,
shared with its maker alone. `rmdir` there removes an empty volume (and
every grant of it). Nothing else can be made, moved or removed in the
root.

  mkdir ~/raft5fs/photos
  cp -r ~/Pictures/2024 ~/raft5fs/photos/
  ls -l ~/raft5fs/photos

There are no owners in the filesystem: everything shows the local user
who mounted it as its owner, and chown to anyone else is refused.
Permission bits are kept and shown (so `chmod +x` works), but grants
decide who may read and write (section 7).

Everything done through the mount is done as alice, whichever local user
does it. That is why the mount is only usable by the local user who
mounted it. Each person mounts with their own login.

  --cache-size <SIZE>  memory for caching file data, decrypted (default
                     64M, 0 disables; or `cache_size` in the profile). A
                     cached chunk is checked with a server on every read
                     -- a few bytes, not the chunk -- so it is never stale.
  --no-write-buffer  store every write at once instead of buffering
                     small writes (slower; mostly for debugging).
  --no-background-prune  don't work through the prune queue while
                     mounted (7.2).

A mount fails over between every server in the profile (or given with
--server, more than once). Shares from people not trusted yet are
read-only (7.3); the mount says so on its terminal the first time it
opens one.

To unmount:

  fusermount3 -u ~/raft5fs

Buffered writes are stored before the unmount completes. A program
that needs to know its data is stored should call fsync, or check the
result of close.

Not supported: hard links, symlinks, device files, and atomically
swapping two names (renameat2 RENAME_EXCHANGE).

6.1 WEBDAV

Instead of mounting, the filesystem can be served over WebDAV, for
whatever WebDAV client the machine has -- Finder, davfs2, GNOME Files
(gio), rclone -- with no kernel module:

  raft5fs webdav                        # http://127.0.0.1:8080/
  raft5fs webdav --listen 127.0.0.1:9000

It asks for alice's password as `mount` does, runs in the foreground,
and takes the same --cache-size, --no-write-buffer and
--no-background-prune. What it serves is what a mount shows: the same
root of volumes, `.snapshot`, and grants.

A WebDAV server is a mount by other means: everything in it is
decrypted, and everything done through it is done as alice. So it
listens on loopback only (anything else is refused), and every request
must carry a password it makes when it starts, which it prints and
writes to $XDG_RUNTIME_DIR/raft5fs/<profile>.webdav (readable by alice
only; under ~/.local/state/raft5fs/run where there is no
$XDG_RUNTIME_DIR, as on macOS). Log in with user `alice` and that
password. Requests naming any host but localhost, 127.0.0.1 or [::1],
or sent from a web page of another origin, are refused too, so a web
page can't reach it through the browser.

  macOS Finder   Go > Connect to Server (Cmd-K): http://localhost:8080/
  davfs2         mount -t davfs http://localhost:8080/ ~/raft5fs
  GNOME Files    Other Locations > Connect to Server: dav://localhost:8080/

Finder litters every directory it opens with `.DS_Store` and `._*`
files; they are refused unless --keep-apple-double is given.

With --password-file FILE the password is kept: made and written to
FILE (readable by alice only) the first time, and used again on every
start after, so a client that saves passwords needs it only once:

  raft5fs webdav --password-file ~/.config/raft5fs/webdav.pw

A PUT is answered only once its body is stored, so a client that
reports a copy done has had it stored. Ctrl-C (or SIGTERM) stops the
server, storing what is still buffered.

6.2 ANOTHER DEVICE

An account works from any number of devices: the keys are unlocked by
the password, wherever it is typed. A second device needs only the
profile -- the servers, their CA, and the keys alice has pinned for
other users (section 7) -- which one line carries:

  raft5fs profile export                # on a device that has the profile
  raft5fs profile import '<line>'       # on the new one

Nothing in the line is secret, but it decides whom the new device
trusts, so move it yourself: a CA swapped on the way would point it at
other servers. A key the new device already pins for a user is kept
over the line's, and said so.


-------------------------------------------------------------------------
7. SHARING
-------------------------------------------------------------------------

7.1 Grants

Grants are of directories, and cover everything under them. A path
starts at an entry of the root, as the mount shows it:

  raft5fs grant photos/2024 bob --ro --name from-alice \
    --fingerprint 'bob's twelve words'

--fingerprint is needed the first time alice shares with bob: it is his
key's, as he read it to her (7.3). bob's root now shows from-alice. --ro
makes the grant read-only, and writes under it then fail with "Read-only
file system"; without it bob may change anything under it, and share it
on. To share, alice needs a read-write grant of the directory -- which
she has of every volume she made.

  raft5fs grants photos/2024        who holds it, and how

Grants alone decide access, and are checked on every request, so a grant
taken back stops even files bob has open, at once.

Moving a file or directory to another directory gives it a new key, so
that whoever could read where it was can't read what is written to it
where it went.

7.2 Revoking

  raft5fs revoke photos/2024 bob

A revocation gives the directory a new key, and new keys for everything
under it before anything new is written there: what is written after it
is sealed under keys bob never had. What bob could read before, he may
have kept a copy of; revoking can't take that back -- and snapshots taken
while he held the grant still show it to him (section 8). Revoking a grant of
a directory needs a grant of the directory above it (its new key is
sealed under that one's), except for a volume.

What was written before stays sealed under the old keys -- which bob
has -- until the directory is pruned: everything under it sealed again
under the new keys, and the old ones dropped. That matters only if bob
also gets hold of the raw store, but it is worth finishing. A revocation
queues the directory for pruning (~/.local/state/raft5fs/, per account
and filesystem), and returns at once. A running mount works through the
queue in the background, a node at a time, leaving the store to what
you are doing; or prune in the foreground:

  raft5fs prune                  everything queued, now
  raft5fs prune --status         what is queued, and how far each has got
  raft5fs prune photos/2024      a directory, queued or not (--dry-run
                                 counts what it would do; --all does
                                 everything shared with you writably)

A prune re-seals all of it, so a big tree takes as long as uploading it
again. `revoke --no-prune` queues nothing.

7.3 Whose key?

Sharing with bob seals the directory's key to bob's public key, and only
the server can say what that is: a server that wanted to read what alice
shares could hand her its own key as bob's. So keys are pinned: the
first grant to bob takes his fingerprint, checked with him, and pins his
key; a different key for him is refused after that. Fingerprints are
twelve words, read out the way bob's `raft5fs whoami` shows them, or 32
hex digits.

It works the other way too. bob's mount opens a grant with the key of
whoever made it, which proves who that was -- but a server could make up
a user, and a share from them, labelled like one bob expects. Until bob
has pinned alice's key, what she shares with him is read-only: he can
look, but nothing he writes could end up sealed under a key the server
made.

  raft5fs pending                what is shared with you by someone not
                                 trusted yet, with their fingerprint as
                                 the server has it
  raft5fs trust alice <her twelve words>
                                 pin her key, if she reads you the same

A running mount takes the new pin the next time it writes there. If
someone really did enrol again, check their new fingerprint with them,
then:

  raft5fs forget-key bob

Pins live in ~/.config/raft5fs/filesystems/<id>/known_keys, where <id>
comes from the CA certificate the profile trusts -- one file per
filesystem, shared by every command and mount for it, and never chosen
by a server. --known-keys puts them elsewhere.


-------------------------------------------------------------------------
8. SNAPSHOTS
-------------------------------------------------------------------------

A snapshot pins the whole filesystem as it is at that moment, for every
user to look back at. Taking and removing them needs a store account in
backup-operators, such as raft5fs (section 3), so with the store options
from section 4:

  raft5fs-server snapshot create daily-2026-10-06 $STORE https://127.0.0.1:27051
  raft5fs-server snapshot list $STORE https://127.0.0.1:27051
  raft5fs-server snapshot del daily-2026-10-06 $STORE https://127.0.0.1:27051

A name is letters, digits, '.', '_', '-', ':' and '+'; leave it out of
`create` to name the snapshot by the time. `list` prints each name with
when it was taken, in seconds since the Unix epoch.

Every mount shows the snapshots under .snapshot in its root, which `ls`
doesn't list -- so `find` and backups of the mount don't wander into
them -- but which is there to go into:

  ls ~/raft5fs/.snapshot
  ls ~/raft5fs/.snapshot/daily-2026-10-06/photos
  cp ~/raft5fs/.snapshot/daily-2026-10-06/photos/cat.jpg ~/raft5fs/photos/

Under each snapshot is the user's root as it was then: what was shared
with them when it was taken, under the names it had, and everything
under that as it stood -- including volumes and files deleted since.
What was shared with them only later isn't there; what was taken back
since still is. Nothing in a snapshot can be changed: it is read-only.

What it costs: until it is removed, a snapshot keeps every version of
everything changed or deleted since it was taken, so the store grows
with every change. The store holds at most 32 at once.


-------------------------------------------------------------------------
9. WHAT THE SERVERS CAN AND CAN'T DO
-------------------------------------------------------------------------

They can't read file contents, names (of files, directories, or what a
grant is called), or passwords; nor forge or alter what is sealed
without the change being detected when it is read. A server can't get a
key sealed to anyone the people sharing it didn't share it with: who
each directory is shared with is kept sealed under its key too, and a
mount re-seals keys only to who is on that list. Nor can it point a name
at another file: every name is sealed bound to the inode it names.

They can see:

  - the shape of the tree, inode numbers, sizes, permission bits and
    times;
  - with large files in a bucket (section 12), which of a file's blocks
    are read and written, and when. Whoever runs the bucket sees as
    much of that as the objects show: each object's size, the inode it
    belongs to, and when it is read or written -- sealed contents only;
  - who is granted what, read-only or not, and who reads and writes
    which inodes, and when;
  - the names of snapshots, which are chosen in the clear;
  - the tag each name is filed under. The tag of a name doesn't change
    when the directory's key does, so someone revoked who also got hold
    of the raw store could test guesses at the names of new files in a
    directory they used to have.

And as the ones holding the data, they can always lose it, withhold
it, change what isn't sealed (sizes, times, permission bits, the tree's
shape), or hand back an older version of something that was really
written once (sealing proves where data came from, not that it is the
latest). In particular:

  - a chunk withheld reads as zeros, like a hole, and a size changed
    makes a file shorter or longer;
  - a mount refuses a directory's key older than one it has already seen
    while it runs, but a newly started one can't tell: a server
    colluding with someone revoked could hand it the old one, and have
    what it then writes sealed under a key they had;
  - a server could show a user a share it made up, from a user it made
    up -- which stays read-only (7.3). The pinned keys are what stop it
    reading what users share with each other, so check fingerprints.

And anyone with a key -- read-only or not -- can write a directory's
sealed list of who it is shared with. Read-only is the servers' rule,
not the keys': someone with a read-only grant and the raw store could
get a key sealed to an account of theirs at the next revocation.

What it costs:

  - The server can't patch an encrypted chunk, so a write smaller than
    a chunk changes the whole chunk: from the mount's cache if it has
    it, or else read, changed and re-sealed. Small, scattered writes to
    files the mount hasn't touched cost more; a smaller --chunk-size,
    chosen when the filesystem is created, helps.
  - Each chunk is stored 44 bytes larger.
  - In a bucket (section 12), a block is replaced whole: a small write
    into one uploads all of it again.
  - A revocation, a grant, and a move to another directory each scan
    every grant in the filesystem. Fine for hundreds; slow for very many.
  - A move to another directory gives what moved a new key, and
    everything under it a new key the next time it is written.

local-fs (in utils) runs a whole installation on one machine, for
trying all this out.


-------------------------------------------------------------------------
10. MORE THAN ONE OF EACH
-------------------------------------------------------------------------

More filesystem servers: start another raft5fs-server, the same way as
in section 4, on any machine that can reach the store, with the same
token.key. Servers keep no state of their own, so a mount can use any of
them, and an open file survives its server restarting.

Changing token.key logs every mount out. Mounts log back in on their
own, from the login secret they kept.

More store nodes: start each node with its own --id and --db, plus the
peer TLS flags (--peer-tls-cert, --peer-tls-key, --peer-tls-ca; every
node must agree), and use --advertise / --advertise-client when nodes
dial each other by addresses other than the ones they bind. Then add it
from the admin shell, connected to the existing cluster:

  raft> add_server https://<new-node>:<peer-port>

See TLS.txt in the jmeisel_raft5 repository for the peer certificate
requirements. Give filesystem servers every store node's client address
as seeds.


-------------------------------------------------------------------------
11. TROUBLESHOOTING
-------------------------------------------------------------------------

  "login refused: the username or password was wrong"
      Also what a user who hasn't enrolled yet gets (section 5).

  "no such enrolment code"
      The code is wrong, was issued to someone else, or was used: codes
      work once. `user add` issues another.

  "Operation not permitted" making a file at the top of a mount
      Only volumes go there: `mkdir` one, and put files in it.

  "the server gave a different key for <user> than before"
      Either they enrolled again or the server is lying. Check their
      fingerprint with them before `raft5fs forget-key <user>`.

  "Permission denied" writing under something shared with you, and
  "... whose key isn't pinned here"
      Whoever shared it isn't trusted yet (7.3): `raft5fs pending` shows
      who; check their fingerprint with them, then `raft5fs trust`.

  "which profile?"
      There is more than one: give --profile (`raft5fs profile list`).

  "... known_keys is no longer read"
      Pins used to be one file for every filesystem. Move each pin into
      the file for its filesystem (7.3), then remove the old one.

  "the server's list of who it is granted to doesn't match the one
  sealed under its key"
      The server says the directory is shared with someone its key
      holders never shared it with. Nothing was sealed to them. If the
      name is no one you know, revoke it; and look into the server.

  "refusing to log in without TLS" / "only https:// addresses"
      Give --ca and https:// addresses (or --insecure-plaintext, for a
      throwaway setup).

  "... can't reach" (revoke)
      Revoking a grant of a directory takes a grant of the one above it;
      ask someone who has one, or revoke at the volume.

  "this store holds a filesystem made by an older raft5fs"
      There is no migrating it; start from an empty store.

  "cannot log in to the store as raft5fs" (filesystem server)
      RAFT5FS_STORE_PASSWORD is wrong, or the store certificate options
      don't match the store's (--store-ca, and --store-cert/--store-key
      if the store requires client certificates).

  "Operation not supported" reading a large file
      It keeps data in object storage (section 12), which this mount is
      too old to read. Upgrade raft5fs on this machine.

  "uploading a block" / "fetching a block: object store refused the
  request (403)"
      The bucket refused a URL a server signed: the servers' key lacks a
      permission, or a server's clock is wrong, or the mount sat on the
      URL too long. On the servers' side, check the key and NTP.

  "... keeps data in object storage, which this server can't reach"
      A server without the object options served a file whose data is in
      the bucket. Give every server the same object options.

  A server that "did not answer"
      Over TLS this is often a refused handshake, not a dead server: a
      missing client certificate, or a certificate whose
      subjectAltName doesn't cover the address dialed.


-------------------------------------------------------------------------
12. LARGE FILES IN OBJECT STORAGE
-------------------------------------------------------------------------

The store keeps every byte on every node, and everything written goes
through one leader. That suits small files. For large ones, the
filesystem servers can keep each file's data past a point in an
S3-compatible bucket instead:

  export RAFT5FS_OBJECT_ACCESS_KEY='<the bucket key>'
  export RAFT5FS_OBJECT_SECRET_KEY='<its secret>'
  raft5fs-server ... \
    --object-endpoint https://s3.eu-west-1.amazonaws.com \
    --object-bucket <BUCKET> --object-region eu-west-1 \
    $STORE https://127.0.0.1:27051

The usage `raft5fs-server` prints with no options covers the rest:
--object-path-style for MinIO, --object-prefix, --object-ca,
--object-from, --object-block and --gc-interval.

How it works. A file made through such a server is "hybrid":

  - Its first --object-from (default 10M) stays in the store, as every
    file's does. Past that, its data goes in blocks of --object-block
    (default 16M), one object each, and the store keeps a 32-byte
    pointer per block.
  - To write a block, the mount seals each chunk of it (zero-padded to
    a whole chunk) and asks a server for an upload URL. The server
    checks the grant and signs a URL for exactly that many bytes,
    usable once. The mount uploads the block, then stores the pointer.
  - To read, a server hands the mount a URL for the block, and the
    mount fetches only the chunks it needs.

Every server of a filesystem should have the same object options. The
first to start records --object-from and --object-block for good. Files
made before keep everything in the store.

Users' mounts must be able to reach the bucket's endpoint. For a bucket
behind a private CA, add the CA to the profile:

  object_ca = "/path/to/s3-ca.pem"

An older mount, which can't read blocks, gets "Operation not supported"
reading a hybrid file past --object-from. It never gets zeros in place
of data.

Garbage. Objects are never changed, only replaced. Every change to a
block -- a write in it, a truncate into it, a prune -- uploads a new
object, and the one it replaces is left behind. Each server with a
bucket sweeps for those every --gc-interval (default 3600 s), one server
at a time:

  - It deletes an object once two sweeps at least --object-get-ttl plus
    five minutes apart have found nothing pointing at it, live or in any
    snapshot.
  - It never deletes one minted too recently to be sure of, or anything
    under the prefix that isn't one of its own object names.
  - A sweep that fails part-way deletes nothing.

A snapshot keeps its blocks for as long as it exists, as it keeps
everything else.

The bucket needs:

  - conditional writes (If-None-Match), which AWS S3 and current MinIO
    support: what stops an upload URL being used to overwrite an object;
  - optionally, versioning, as a safety net for garbage collection.
    Backups (section 13) copy the objects they need, so they don't
    depend on it. A copy of the store made some other way does: its
    pointers may name objects deleted since;
  - a key allowed to get, put, delete and list under the prefix, and
    nothing else. Every URL the servers sign acts with its rights;
  - the servers' clocks kept right (NTP): upload names carry the time
    they were minted, and a commit too long after that is refused.

What it costs. A block is replaced whole, so a small write into one
fetches whatever of it isn't cached and uploads the whole block again.
A mount also holds up to a block per file being written before it
uploads it. Large files written front to back, and read back, are what
this is for. Small random writes into large files (databases, VM images)
do better with a smaller --object-block, or in a filesystem without a
bucket.


-------------------------------------------------------------------------
13. BACKUPS
-------------------------------------------------------------------------

A backup copies a snapshot to a backup space: an S3-compatible bucket
that is not the one the servers keep objects in, ideally somewhere else.
It holds:

  - the store's own backup of the snapshot (every key, account, group
    and ACL), sealed to an operator key pair;
  - every object the snapshot points to (section 12). Backups share
    these, so each copies only objects that no earlier backup has.

Everything the mounts sealed stays sealed. The operator key also seals
what the store holds in clear (accounts' verifiers, sizes, layout), so
whoever can read the backup space can't use those either.

The operator key pair. Make it on a machine you trust, give the servers
only the public key, and keep the private key offline: it opens the
store contents of every backup.

  raft5fs-server backup keygen backup.key   # also writes backup.key.pub

The backup options, with the space's credentials in
RAFT5FS_BACKUP_ACCESS_KEY and RAFT5FS_BACKUP_SECRET_KEY:

  BACKUP="--backup-endpoint https://... --backup-bucket raft5fs-backups \
          --backup-region ... --backup-public-key backup.key.pub"

  --backup-prefix  what every key starts with (default raft5fs-backup/).
  --backup-path-style, --backup-ca  as for the --object-* options.

Taking one. Snapshot first, then back the snapshot up under its name,
with the store options from section 4 and, if the filesystem keeps
objects, the --object-* options from section 12 ($OBJECTS):

  raft5fs-server snapshot create nightly-1 $STORE https://127.0.0.1:27051
  raft5fs-server backup create nightly-1 $STORE $OBJECTS $BACKUP https://127.0.0.1:27051
  raft5fs-server backup list $BACKUP

A backup is whole once its manifest is written, last. One that fails
part way leaves files with no manifest, which `backup del` cleans up. An
object the snapshot points to that is missing fails the backup, rather
than leaving a backup that can't be restored. Once it is made, the
snapshot can go (`snapshot del`).

  raft5fs-server backup del nightly-1 $STORE $BACKUP https://127.0.0.1:27051

deletes the backup, then every object in the space that no other backup
needs. One backup job (create or del) runs at a time; another waits for
it to finish, or for its lease to run out after ten minutes.

Restoring, into a new store and an empty bucket:

  1. Copy the objects into the bucket the restored servers will use,
     under the same prefix as before:

       raft5fs-server backup restore-objects nightly-1 $OBJECTS $BACKUP

  2. Open the store contents with the private key:

       raft5fs-server backup fetch-kv nightly-1 store.backup \
         --backup-private-key backup.key $BACKUP

  3. Start a new, empty store node (section 3) and bootstrap it from
     them instead of creating accounts by hand:

       raft> bootstrap n1 --restore-from store.backup

  4. Start the servers (section 4). Users log in as before.

Accounts, groups and ACLs come back with the store; snapshots don't.
Delete store.backup when done: it holds the store's contents in clear.


-------------------------------------------------------------------------
14. ANDROID (TERMUX)
-------------------------------------------------------------------------

An Android phone can't mount, but it can run `raft5fs webdav` (section
6.1) in Termux, for a WebDAV file manager on the same phone. Everything
is decrypted on the phone, as on a computer; the servers see no more
than before.

Each release has the binary, raft5fs-android-aarch64 (64-bit ARM, the
usual kind of phone), built without FUSE.

Setting it up, once:

  1. From F-Droid, install Termux (the Play Store's Termux is out of
     date), and a file manager that speaks WebDAV: Material Files is
     free; Solid Explorer and CX File Explorer work too.

  2. In Android's settings, under Apps > Termux > Battery, choose
     "Unrestricted". Otherwise Android stops the server in the
     background, and the file manager finds nothing.

  3. In Termux, install the binary, checking it against its checksum.
     The script picks the Android build and installs it in
     $PREFIX/bin, which Termux already has on its PATH:

       pkg update && pkg install curl
       curl -fsSLO https://raw.githubusercontent.com/jonathanmeisel/jmeisel_raft5_fuse/master/deploy/get-raft5fs.sh
       sh get-raft5fs.sh

     or by hand:

       url=https://github.com/jonathanmeisel/jmeisel_raft5_fuse/releases/latest/download
       curl -LO $url/raft5fs-android-aarch64 -LO $url/SHA256SUMS
       sha256sum -c SHA256SUMS --ignore-missing
       install -m 755 raft5fs-android-aarch64 $PREFIX/bin/raft5fs

  4. Make the profile (section 6.2). On your computer:

       raft5fs profile export

     Get the line to the phone yourself (a note to yourself, a password
     manager), then in Termux:

       raft5fs profile import '<line>'

     A new user, with no account yet, enrols on the phone instead:
     raft5fs enrol '<invitation>' (section 5).

  5. Start the server (step 6 below), then add it in the file manager:
     a WebDAV server at host 127.0.0.1, port 8080, plain HTTP (not
     HTTPS), path /; user: the account's name; password: what
     `cat ~/.config/raft5fs/webdav.pw` shows in Termux.

Each time the phone starts (the password is never stored, so this is
done by hand):

  6. In Termux:

       termux-wake-lock
       raft5fs webdav --password-file ~/.config/raft5fs/webdav.pw

     and type the account's password. Leave Termux running; its
     notification shows it is. The wake lock keeps the server running
     with the screen off.

  7. To stop it: Ctrl-C in Termux, which stores what is buffered first,
     then termux-wake-unlock.

To update, repeat step 3. To remove it: rm $PREFIX/bin/raft5fs and
rm -r ~/.config/raft5fs.

If the file manager can't connect: check Termux still shows the server
running (Android may have stopped it: see step 2), that the address is
http://, not https://, and that the password matches webdav.pw. If large
files fail to open while small ones work, the phone can't reach the
object store: check its network, and that the bucket's address in the
servers' settings is reachable from outside.
